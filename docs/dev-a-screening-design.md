# Cheap dev-A screening subset

Status: design only. Membership is not generated by this document. Generation
happens inside the optimization loop, under a committed seed, before any
candidate outcome for the screened candidate exists.

Bead: `omni-benchmark-ei0.11.5`. Parent: `omni-benchmark-ei0.11`.

## 1. Problem

Each optimization iteration currently costs a 16-database deploy, a full dev-A
promotion run, freeze, and scoring. The promotion run schedules all 154 dev-A
questions; 136 of them are scoreable after the 18 identities in
`config/conditions/dev-a-scorer-conformance-exclusions-v1.json` are removed for
gold statement errors. At that price the MVP supports roughly two to four
KEEP/REVERT cycles.

Weak candidates currently consume a full promotion run before they are
rejected. A small fixed subset of dev-A can absorb that rejection at about a
quarter of the attempt cost, provided the subset is chosen before any candidate
outcome is visible and provided it can only reject or order candidates, never
promote one.

## 3. Selection

Size is 32, the top of the 24-32 band the bead allows. Section 6 shows why the
largest permitted size is the right choice: every leg of the decision rule is
power-limited, and the marginal cost of four extra attempts is negligible
against the 104 attempts a rejection saves.

### 3.1 Algorithm

Name: `database_high_level_sha256_screen_v1`. It follows the D-054 precedent
(`database_high_level_sha256_sensitivity_v1`) with the remainder machinery
removed, because an equal per-database allocation of 32 over 16 strata is exact.

1. Build the answerable population as in section 2.
2. Allocate exactly 2 questions to each of the 16 databases.
3. Within a database, if both `high_level` strata are non-empty, take 1 from
   each. If one stratum is empty, take both from the non-empty stratum.
4. Within a stratum, order candidates ascending by the lowercase hex digest of
   `SHA-256(seed || US || database || US || high_level || US || instance_id)`,
   where `US` is the byte `0x1f` and `high_level` is rendered as `true` or
   `false`. Take the first k. Ties cannot occur; equal digests would fail the
   generator.
5. Emit the selected identifiers sorted lexicographically.

Equal allocation is chosen over proportional allocation. The population is
already close to uniform (13 of 16 databases hold 9 to 11 questions, three hold
5), so the two designs differ only in whether the three small databases are
weighted at 2/5 or 1/5. Equal allocation gives every database identical weight,
which matches the loop's second-ranked objective of cross-database generality,
and it keeps the algorithm auditable without floating-point remainders. The cost
is that subset accuracy is a mildly biased estimator of full-frame accuracy. That
bias is immaterial because, per section 5, the accuracy leg is a floor test and
not an estimate of the full-frame rate.

### 3.2 Resulting composition

The allocation is fully determined by public counts before any digest is
computed:

- 2 questions from each of the 16 databases.
- 11 databases contribute one question from each `high_level` stratum.
- `cybermarket_pattern_large` and `reverse_logistics_large` contribute 2
  `high_level` false; `museum_artifact_large`, `robot_fault_prediction_large`,
  and `virtual_idol_large` contribute 2 `high_level` true.
- Total: 17 `high_level` true, 15 false. The population share is 71/136
  (52.2%); the subset share is 53.1%.

`conditions` marginals (`order`, `distinct`, `decimal`) are not balanced by the
algorithm. They are recorded in the artifact as observed distributions so a
reader can see what the draw produced, matching the D-054 metadata convention.

### 3.3 Anti-cherry-pick lock

Membership and the section 5 thresholds are frozen in the same committed file.
The experiment proposal records that file's SHA-256 before the screen runs, and
the screen runner validates the artifact from git at the recorded commit rather
than from the working tree. Membership never changes in response to any
candidate outcome. If a later change to the population or the algorithm is
justified for a non-outcome reason, it ships as `-v2` alongside `-v1`; the
existing file is never edited or deleted, and the loop declares which version it
uses before the screen runs.

## 4. What the screen is for

The screen answers one question: is there positive evidence that this candidate
is broken or inert, sufficient to skip the promotion run? It does not estimate
accuracy, and it cannot supply evidence for KEEP.

Three legs, in priority order.

**Leg 1, mechanism firing (deterministic).** Every proposal declares one
mechanism. The screen checks, per attempt, whether that mechanism is observable
in the trace fields already specified in `config/autoresearch.json`
(`semantic_objects_retrieved`, `generated_query`, `compiler_status`,
`validation_status`, and the rest). If the declared mechanism does not fire on
the subset, the full run cannot test the hypothesis, and the correct action is
to fix the candidate rather than spend 136 attempts. This leg is not
statistical and has effectively full power at n = 32.

**Leg 2, regression suite and error rate.** The append-only dev-A regression
suite is evaluated in full, independently of the 32-question draw; any capability
break is a rejection regardless of every other signal. Separately, the screen
counts refused and system-error terminal outcomes on the subset. The C4 baseline
rate is 34/136 (25.0%), so the expected subset count is 8.

**Leg 3, accuracy floor.** The screen counts correct answers on the subset
under both frozen scorers. This is a signs-of-life test, not a superiority test.

## 5. Decision rule

Reject a candidate before the promotion run when any of the following holds.

| Gate | Rule |
| --- | --- |
| Mechanism | The declared mechanism fires on 0 of the 32 attempts. |
| Regression | Any regression-suite capability that the parent candidate held is lost. |
| Error rate | Refused plus system-error outcomes on the subset are 14 or more of 32. |
| Accuracy floor | The candidate scores 0 correct of 32 under both frozen scorers, and the accuracy leg is operative (section 5.2). |

Otherwise the candidate proceeds to the full promotion run. Passing the screen
carries no weight in the KEEP decision. It means only that the loop did not find
positive evidence of breakage.

### 5.1 Error-rate threshold trade-off

Binomial at the baseline error rate of 0.250 and at three elevated rates:

| Rejection threshold | False reject at 25.0% | Power at 40% | Power at 45% | Power at 50% | Power at 60% |
| --- | ---: | ---: | ---: | ---: | ---: |
| >= 13 of 32 | 3.8% | 0.54 | 0.75 | 0.89 | 0.99 |
| >= 14 of 32 | 1.6% | 0.40 | 0.62 | 0.81 | 0.98 |
| >= 15 of 32 | 0.6% | 0.27 | 0.48 | 0.70 | 0.95 |

The rule uses 14. That accepts 1.6% false rejection of a candidate whose true
error rate is unchanged, in exchange for detecting a doubling of the error rate
(25% to 50%) four times in five. A candidate that merely nudges the error rate
up will pass the screen and be judged on the full run, which is the intended
asymmetry.

### 5.2 Accuracy-floor trade-off

The baseline C4 accuracy is 9/136 (6.6%). At n = 32 the expected correct count
is about 2. The screen therefore cannot detect improvement; it can only detect
the total absence of correct answers.

Probability that a candidate produces 0 correct on 32 questions, by true
accuracy:

| True accuracy | P(0 correct of 32) |
| --- | ---: |
| 6.6% (baseline) | 11.3% |
| 10.0% | 3.4% |
| 13.0% (2x baseline) | 1.2% |
| 15.0% | 0.6% |

Read this as: the accuracy floor discards a genuinely doubled candidate about 1
time in 80, and a candidate indistinguishable from baseline about 1 time in 9.
The false-rejection risk is concentrated on candidates that could not have
produced KEEP evidence anyway. Combined with leg 2, a candidate identical to
baseline in every respect is falsely rejected about 12.7% of the time, and a
candidate at 13% true accuracy with an unchanged error rate about 2.7% of the
time.

What the accuracy leg cannot do is worth stating plainly. A candidate that moves
accuracy from 6.6% to 9% shows 2 or 3 correct against a baseline expectation of
2. No threshold on 32 questions separates those. The screen must never reject on
"fewer correct than baseline", and the rule above deliberately contains no such
comparison.

**Operativeness.** Once membership is frozen, the loop computes from the frozen
baseline score artifact how many subset questions the baseline answers correctly
and records that count in the artifact under `baseline_reference`. This is a
one-time post-freeze annotation that never alters membership, and it depends on
the baseline only, never on a candidate. Under a 32-of-136 draw the expected
count is 2.1, with an 8.2% chance of 0 and a 32.8% chance of at most 1. If the
recorded count is 0 or 1, the accuracy leg is declared non-operative for every
screen against `-v1` and the rule reduces to legs 1 and 2. Declaring this at
freeze time, from a fixed prior artifact, is what keeps it from becoming a
post-hoc escape.

### 5.3 Rejection is terminal

A screen-rejected candidate is not re-screened. Resurrection requires the full
promotion run, decided on the mechanism, not on a second draw. Without this,
repeated screening of the same candidate would convert an 11% false-rejection
rate into a candidate-selection procedure that optimizes against 32 questions.

## 6. Cost model

Unit: one C4 attempt on the governed dev-A path. A promotion run schedules 154
attempts and scores 136; the bead's 136-attempt figure is the scored frame, so
both accountings appear below.

| Quantity | Attempts |
| --- | ---: |
| Full promotion run (scored frame) | 136 |
| Full promotion run (scheduled) | 154 |
| Screen | 32 |
| Saved per rejected candidate (scored frame) | 104 (76.5%) |
| Saved per rejected candidate (scheduled) | 122 (79.2%) |
| Overhead per candidate that passes | 32 (23.5% of a promotion run) |

Break-even pass rate against the 136 frame: screening is net-cheaper when fewer
than 76.5% of screened candidates pass. Against the 154 frame the break-even is
79.2%. Total attempt cost for k candidates with pass fraction q is
`32k + 136qk`, a ratio of `0.235 + q` against running all k in full.

| Scenario | Screened cost | Unscreened cost | Saved | Equivalent full runs freed |
| --- | ---: | ---: | ---: | ---: |
| 4 candidates, 1 passes | 264 | 544 | 280 (51%) | 2.1 |
| 6 candidates, 2 pass | 464 | 816 | 352 (43%) | 2.6 |
| 8 candidates, 3 pass | 664 | 1088 | 424 (39%) | 3.1 |
| 6 candidates, 4 pass | 736 | 816 | 80 (10%) | 0.6 |
| 6 candidates, 5 pass | 872 | 816 | -56 (-7%) | none |

The last row is the failure mode: if the loop screens only candidates it already
believes in, screening costs more than it saves. The screen is worth running
when the loop is generating variants faster than it can afford to promote them,
which is the situation the parent bead describes.

**What screening does not save.** The 16-database deploy is per-candidate, not
per-attempt, and the screen covers all 16 databases, so the candidate must be
fully deployed before it can be screened. Screening saves the attempt leg and
the scoring leg only. A database-restricted screen would save deploy cost as
well, and it is rejected: it cannot detect database-specific regressions, and it
would bias the loop toward interventions that happen to help the sampled
databases, against the generality objective.

**Money and wall clock.** No per-attempt C4 cost is published. The only
per-attempt reference in `RESULTS.md` is the $1.48 to $1.84 band for C1-C3, and
that is a direct-comparator figure, not a C4 estimate. Convert attempts to
dollars and seconds using the candidate's own observed C4 attempt mean at the
time of screening, and record the observed figure rather than a projection.

## 7. Protocol compatibility

No protocol change is required, and none is proposed. Split membership, custody
rules, scoring definitions, endpoints, and the protocol remain
human-controlled surfaces.

**The KEEP gate is untouched.** `EVALUATION_PROTOCOL.md` requires that "a `KEEP`
decision requires a complete 154-question `dev-A` evaluation and an explicit
generality/regression/complexity rationale; aggregate accuracy alone is
insufficient." `config/autoresearch.json` sets
`acceptance_policy.keep_requires_complete_dev_a_run` to `true`. The screen
produces no KEEP and is never cited as KEEP evidence. It filters and orders the
queue of candidates that have not yet reached the gate. The gate's input,
threshold, and evidence requirements are identical with and without the screen.

**It instantiates an existing step.** `docs/autoresearch.md` step 4 already
provides for a prespecified training slice, "declared before results and never
selected from favorable outcomes." This design replaces a per-experiment
declaration with one standing committed slice, which is strictly stronger: a
slice re-declared per experiment can drift toward whatever the experimenter
expects, and a frozen slice cannot.

**It does not violate the rejected-pattern list.** `docs/autoresearch.md`
rejects "acceptance based on a favorable subset." The screen never accepts. Its
only two outputs are rejection and no-decision. A candidate that passes has
learned nothing about its own promotion prospects.

**Adaptive reuse is already permitted.** The protocol states that "autoresearch
may repeatedly observe and score only `dev-A`." The subset is a strict subset of
dev-A and opens no new data access. Reusing the same 32 questions across
candidates does compound overfitting risk against that subset, and section 5.3
plus the reject-only asymmetry are the controls: nothing is promoted on subset
evidence, and no candidate gets a second draw. Every KEEP is still computed on
the full frame, which contains the 32.

**No dev-B, test, or hidden-annotation contact.** Selection reads
`selected_database` and `high_level` from the public eligible manifest. No gold
SQL, test case, `external_knowledge` ID, hidden annotation, dev-B outcome, or
test identity is involved at any stage.

**Ledger discipline.** A screen result is appended to the ledger before the full
run is launched or the candidate is abandoned. A screen-based rejection is
recorded as `REVERT` or `ARCHIVE` with `evaluation_scope` set to
`screen_subset`, so no reader can mistake it for a full-run `REVERT`. Screen
attempts run under their own immutable run IDs. The rerun policy applies to
them unchanged: a screen attempt that fails inside the evaluated system is a
real outcome, and only a demonstrable failure outside the evaluated system
permits a rerun.

**Stopping policy.** A screen-based rejection counts as a non-KEEP experiment
for the `review_after_consecutive_non_keep_experiments` trigger of 4. Screening
makes non-KEEP outcomes cheaper, which makes the trigger fire sooner in wall
clock; that is the intended behavior and not a reason to exempt screens from the
count.

## 8. Artifact plan

### 8.1 Files

| Path | Role |
| --- | --- |
| `config/conditions/dev-a-screen-subset-v1.json` | Frozen membership, provenance, and decision-rule thresholds. Committed. |
| `src/omni_benchmark/dev_a_screen_subset.py` | Deterministic generator. |
| `scripts/make_dev_a_screen_subset.py` | CLI wrapper, mirroring `scripts/make_c1_retrieval_sensitivity.py`. |
| `tests/test_dev_a_screen_subset.py` | Byte-identical regeneration test plus stratification and population assertions. |

D-054 split its subset across `data/manifests/*_ids.txt`, a metadata JSON, and a
condition file. This design uses one committed file in `config/conditions/`,
per the bead. Membership and the thresholds that read it are frozen under one
SHA-256, so an experiment proposal that records that hash has pinned both. The
file is regenerated, never hand-edited, in line with the repository's manifest
rule.

Do not create the membership file from this document. It is generated in the
loop, under the committed seed, before the first screened candidate produces any
outcome.

### 8.2 Schema

Top-level keys, sorted, `schema_version` 1:

- `algorithm`: `{name, seed, unit, database_allocation, within_database_stratum,
  within_stratum_order}`. Mirrors the D-054 metadata block.
- `baseline_reference`: `{baseline_run_id, baseline_score_artifact_sha256,
  correct_in_subset, refused_or_error_in_subset, accuracy_leg_operative,
  recorded_at}`. Written once after membership freeze; never revised.
- `counts`: `{population_questions: 136, population_databases: 16,
  selected_questions: 32, selected_databases: 16}`.
- `decision_rule`: `{mechanism_fires_minimum: 1,
  refused_or_error_rejection_threshold: 14,
  accuracy_floor_rejection_threshold: 0, scorers:
  ["official_soft_ex", "corrected_multiset_sensitivity"],
  regression_suite_break_rejects: true, rejection_is_terminal: true,
  screen_pass_authorizes_keep: false}`.
- `distributions`: `{by_database: {db: {population, population_high_level,
  selected, selected_high_level}}, overall: {population: {...},
  selected: {...}}}`, including observed `conditions` marginals.
- `instance_ids`: 32 identifiers, sorted lexicographically.
- `kind`: `dev-a-screen-subset`.
- `partition`: `dev-A`.
- `quotas`: `{db: 2}` for each of the 16 databases.
- `schema_version`: `1`.
- `scope`: `candidate-prescreen-before-full-dev-a`.
- `sources`: `{eligible_manifest: {file, sha256}, dev_a_ids: {file, sha256},
  scorer_conformance_exclusions: {file, sha256}, freeze_a_commit}`. The three
  hashes must equal those already recorded in
  `dev-a-scorer-conformance-exclusions-v1.json` for the manifest and dev-A IDs;
  the generator asserts this and fails closed on mismatch.

The file carries no question text, no SQL, no result, and no per-question
outcome. Only `baseline_reference` holds counts derived from an outcome
artifact, and those are aggregates over the subset.

### 8.3 Seed convention

`omni-livesqlbench-<artifact-slug>-v<N>`, following D-054's
`omni-livesqlbench-c1-retrieval-sensitivity-v1`. For this artifact:

```
omni-livesqlbench-dev-a-screen-subset-v1
```

The slug matches the artifact basename without the extension. `N` matches the
file's version suffix. The seed is recorded inside the artifact it produced, so
regeneration needs no external state. A new version increments `N` in both the
filename and the seed and never reuses the previous seed, which guarantees a
`-v2` draw is not a subset-preserving perturbation of `-v1`.

### 8.4 Generator constraints

- Reads only `dev_a_ids.txt`, `eligible_questions.jsonl`, and
  `dev-a-scorer-conformance-exclusions-v1.json`.
- Opens no score artifact, no run artifact, no private release, and no dev-B or
  test manifest. This is asserted in the test, not only documented.
- Refuses to write over an existing file, matching `_write_exclusive`
  semantics. A botched artifact is fixed forward as a new version.
- Emits sorted keys and no NaN, so the SHA-256 is stable across runs.
- Fails closed if any database has fewer than 2 answerable questions, if the
  population is not 136 over 16 databases, or if any source hash does not match
  the recorded value.
